## 1. Checks that claimed more than they checked

### 1.1 CI red for six days

22 runs on `main` failed, `adbc3c7` (10-11) to `1b2bdf0` (10-17); the last green run was
`52822fe` (10-10). Every one failed **only** the mypy ratchet: CI counted 121 against a
baseline of 96, a constant gap of 25 (134 vs 109 on the first). Two causes:

- CI checks as Linux. `msvcrt.kbhit`, `ctypes.windll` and `subprocess.CREATE_NO_WINDOW` -
  Windows-only calls the product makes - are errors there and not on this PC.
- CI installs `types-beautifulsoup4`, stubs written for bs4 4.12, over bs4 4.14.3's own
  types; this PC does not have it. The scraper errors (`NavigableString` has no `find_all`)
  are CI's alone.

From `adbc3c7` on, the baseline was lowered from this PC's count, so CI could never pass.
Fixed by decision §62 (`platform = "win32"`, no 4.12 stubs). The push's CI run (`54f641b`)
passed the type check for the first time since 10-10: 90 errors against the baseline of 92.
The baseline stays at 92 until this PC counts the same; a gap left then is an installed
package, which #457 (a lockfile) closes.

The same run failed both test jobs on one module: `tests/test_backlog_evidence_wave.py`
(`bef5a56`) imports `hypothesis`, which only the dev extra installs, and CI's test jobs
install `.[shell,app]`. They install `hypothesis` now, so the property tests run in CI. Filed #1263: `ops status` says when CI on `main` is red -
nothing in the operator's or the agents' day showed it.

### 1.2 The suite reached the real Postgres (#1247)

On 10-16 a command built a list of test modules, a lint failure left it empty, and a bare
`python -m unittest` ran the whole suite from the repo root with the real `.env`: 133 fake
publish-log rows, 10 performance entries and 1 topic score went into the operator's Postgres,
and real job 59 (run 155's upload) was marked failed. Nothing was uploaded and no file was
written; the rows were deleted and job 59 reset with the operator's yes.

Cause: discovery from the root imports packages in name order; `publishing/__init__` and
`storage/__init__` load `config.settings`, which reads `.env` and freezes
`Settings.database_url`, before `tests/__init__.py` can blank it. Two guards now:
`tests/__init__.py` refuses to load when settings came first (a bare run loads none of the
suite), and `storage/db.py` opens no network database while `CONTENT_SUITE=1` unless it is
CI's own `CONTENT_TEST_DATABASE_URL`. `tests/test_grand_audit.py` runs the bad order in a
child process with a sentinel URL.

`data/launch_state.json` when it existed. It compares the file before and after now.
